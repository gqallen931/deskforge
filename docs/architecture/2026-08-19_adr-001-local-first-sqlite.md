# [单机阶段采用本地 SQLite]  —  Architecture Decision Record

| 字段 | 内容 |
|------|------|
| 日期 | 2026-08-19 |
| 状态 | Accepted |
| 编号 | ADR-001 |
| 关联项目 | Deskforge |

---

## 背景

Deskforge 的第一阶段目标是可安装到 Windows 的个人工作台。用户本机已有 MySQL 8.1，但要求最终用户安装和维护数据库服务会显著增加部署成本，且单机任务数据不需要服务端数据库能力。

---

## 决策

单机阶段使用 Electron/Node 内置 `node:sqlite`，数据库保存在 `%APPDATA%/Deskforge/deskforge.db`；不接入 MySQL 和独立后端。

---

## 备选方案

| 方案 | 描述 | 优势 | 劣势 | 评分 |
|------|------|------|------|------|
| A | SQLite 本地数据库 | 零服务、易打包、离线可用 | 当前 API 有实验性标记 | 9/10 |
| B | 本机 MySQL 8.1 | 成熟、适合多用户服务 | 安装配置复杂、需要账号密码和后台服务 | 5/10 |
| C | JSON 文件 | 实现最短 | 查询、事务、迁移和并发能力弱 | 6/10 |

---

## 后果

| 类型 | 内容 |
|------|------|
| ✅ 正面 | 最终用户无需安装数据库，应用可完全离线运行 |
| ⚠️ 负面 | 需要关注 Electron 版本对 `node:sqlite` 的稳定性 |
| 🔮 风险 | 跨设备同步与多人协作需要新增服务端数据层和迁移方案 |

---

## 面试要点

### 为什么不用 MySQL？
- 单机应用使用 MySQL 会引入服务安装、端口、凭据、升级和备份等不必要的运维成本。

### 什么情况下会推翻这个决策？
- 产品增加多用户协作、跨设备实时同步或集中式权限管理时。

### 这个决策影响了哪些下游模块？
- Electron 主进程、Preload IPC、数据迁移、备份恢复和 Windows 打包。
