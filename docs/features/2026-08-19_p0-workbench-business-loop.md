## 需求背景

任务 CRUD 已经真实化，但侧栏项目、文件、日程、团队、分析、知识库以及工作区、通知、标签仍缺少完整业务闭环。P0 阶段目标是让本地个人工作台的核心入口具备可操作、可持久化、可恢复的数据能力。

---

## 设计思路

### 方案对比

| 方案 | 优点 | 缺点 | 为什么选/不选 |
|------|------|------|-------------|
| 每个按钮直接写 SQL | 快 | 逻辑分散、难测试 | 不选 |
| 统一 WorkbenchService | 边界清晰、便于备份和测试 | 增加一层服务 | 选择 |
| 增加独立 HTTP 后端 | 未来可远程访问 | 单机版部署复杂 | 暂不选择 |

**最终选择：** 继续采用 Renderer → Preload → Electron Main Service → SQLite；文件系统操作只在 Main 中执行。

---

## 核心实现

### 新增数据表

| 表 | 用途 |
|----|------|
| `workspaces` | 工作区与当前激活状态 |
| `projects` | 当前工作区项目 |
| `tags` / `task_tags` | 标签及任务多对多关联 |
| `workspace_files` | 文件路径与元数据，不复制原文件 |
| `notifications` | 逾期和本地业务通知、已读状态 |

### 数据流 / 调用链

```text
侧栏/头部按钮
→ Dashboard Modal / Dropdown
→ window.deskforge.workbench/projects/files/tags/notifications
→ Preload IPC
→ WorkbenchService 参数化 SQL
→ SQLite
→ 返回结果并刷新统计或列表
```

### 完成入口

- 工作区创建、切换。
- 项目创建、列表、归档。
- 文件选择、归档、打开、移除记录。
- 任务标签创建与关联。
- 逾期通知生成、列表、全部已读。
- 项目/任务/文件跨模块搜索。
- 今日待办、进行中、已完成、逾期统计。
- 日程、团队和分析面板使用真实任务数据。
- 个人资料复用真实设置；关闭按钮退出桌面应用。
- 消息入口明确为单机模式未启用，不再显示虚构消息。

### 备份兼容

JSON 格式升级到 v2，新增工作区、项目、标签关联、文件和通知；导入仍接受 v1，并自动创建默认工作区。

## 技术难点

### 难点 1: 文件安全
- **挑战：** 归档按钮不能误删用户磁盘文件。
- **解决：** SQLite 仅保存路径和元数据，“移除”只删除数据库记录；打开前必须验证路径属于已登记记录。

### 难点 2: 新模型纳入备份
- **挑战：** 新表上线后旧备份格式不完整。
- **解决：** v2 导出全部本地业务数据，恢复按外键顺序执行；v1 自动补默认工作区。

### 难点 3: 多弹窗真实 EXE 验收
- **挑战：** 连续测试时关闭动画导致弹窗短时并存，读取第一个节点会误报。
- **解决：** 验收前清理残留弹窗，并始终检查最后打开的弹窗。

## 面试要点

### 如果让你重新设计，会怎么改进？
- 将 Dashboard iframe 逐模块迁移为 React 组件，并引入数据库迁移版本表。

### 涉及哪些设计模式？
- Service Layer、Bridge、Repository、Facade 和多对多关联模型。

### 性能 / 安全 / 扩展性考量？
- 参数化 SQL、最小 Preload API、文件路径白名单验证、事务恢复；未来 Service 可复用到同步后端。
