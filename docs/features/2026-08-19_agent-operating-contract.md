## 需求背景

长期对话中形成了大量稳定规则，包括 A-UI 视觉保真、Deskforge 品牌、本地单机方向、SQLite/IPC 安全边界、AI 与消息禁改、发布暂缓和强制文档记录。若迁移到没有历史对话的 Agent，这些约束可能丢失并造成视觉重做、架构偏移或数据风险。

---

## 设计思路

### 方案对比

| 方案 | 优点 | 缺点 | 为什么选/不选 |
|------|------|------|-------------|
| 仅继续写开发日志 | 历史完整 | 新 Agent 不一定主动发现，规则分散 | 不选 |
| 每种 Agent 各维护一份完整规则 | 入口明确 | 多份规则容易产生版本漂移 | 不选 |
| `AGENTS.md` 单一事实源 + 多入口指针 | 跨工具通用，维护集中，容易发现 | 需要各 Agent 遵循入口约定 | 选用 |

**最终选择：** 在仓库根目录创建完整 `AGENTS.md`，并由 `CLAUDE.md`、`.github/copilot-instructions.md` 和 `README.md` 指向同一事实源。

---

## 核心实现

`AGENTS.md` 固化以下规则：

- 项目名称、目录边界、私有 GitHub 仓库与 Windows 本地产品方向。
- `A-UI/展示` 是唯一视觉基准，仅允许替换为 DF / Deskforge 品牌。
- React 渐进迁移不得以移除 iframe 为由破坏布局和动画。
- AI 建议与消息必须保持“正在开发中”。
- React → Preload → Main → SQLite 的安全数据链路。
- 本地鉴权、用户数据、备份和迁移保护要求。
- 发布、云同步和多人协作在未明确请求时不进入范围。
- 每次任务的检查、测试、文档与 Git 操作清单。
- 冲突处理优先级和新 Agent 快速入场问题。

### 读取链路

```text

Claude Code → CLAUDE.md → AGENTS.md
GitHub Copilot → .github/copilot-instructions.md → AGENTS.md
人类贡献者 → README.md → AGENTS.md
```

## 技术难点

### 难点 1：规则完整与可维护性

- **挑战：** 规则过短会丢失历史意图，多处复制又会产生冲突。
- **解决：** 完整规则只写入 `AGENTS.md`；工具专用文件仅作为入口，不复制业务约束。

### 难点 2：区分长期约束与历史状态

- **挑战：** 安装包版本和测试结果会变化，不应全部固化成永久规则。
- **解决：** `AGENTS.md` 记录稳定合同和当前阶段边界；版本结果继续由 `docs` 维护。

## Reader Test

使用无历史上下文的阅读问题检查文档是否能独立回答：项目范围、视觉基准、可改品牌、AI/消息状态、数据库、IPC 安全、未来后端、测试要求、发布边界、任务结束文档要求。十项均可直接从 `AGENTS.md` 得到无歧义答案。

## 面试要点

### 如果让你重新设计，会怎么改进？

- 后续可在 CI 中增加规则文件存在性与文档索引检查，但避免构建复杂的自定义治理框架。

### 涉及哪些设计模式？

- Single Source of Truth：完整规则集中于 `AGENTS.md`。
- Adapter：不同 Agent 的标准入口都指向同一规则文件。
- Checklist：将隐性经验转换为可验证的交付门禁。

### 性能 / 安全 / 扩展性考量？

- 不包含密码、令牌或个人数据。
- 新 Agent 无需读取完整历史对话即可安全开始工作。
- 持久规则改变时必须同步架构文档，降低规则与实现脱节风险。
